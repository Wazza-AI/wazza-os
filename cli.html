    The command line

    Everything you click in Wazza OS, a terminal can do too. wazza --gui … commands talk to the Wazza OS that is running for you, in the background, and answer in JSON: for scripts, for a server with no screen, and for agents outside Wazza OS.

    Whatwazza --gui commands for the running Wazza OS, and wazza --check
    WhyRepeatable setups, scripts, servers, other agents
    WhoDevelopers, admins, power users
    WhereAny terminal of the same user as the running Wazza OS

    Before you start#

    • wazza, wazzaos and wazza-os are the same program; this manual writes wazza.
    • Wazza OS must be running for the same user: wazza --gui status says so. The commands never open a second window, and only change what you see when you ask (the --focus options).
    • Answers are JSON on standard output. Exit codes: 0 done; 1 refused, failed, or Wazza OS not reachable; 2 the command was wrong and nothing was sent (the usage is printed).
    • Passwords, keys and tokens are read only from standard input (--stdin, --password-stdin, --key-stdin), never as a word of the command: they stay out of your shell history and the process list.
    • wazza --version prints the program's version and the installed package's (version, build and date).
    • For agents that take MCP servers rather than a shell, wazza-os mcp offers these same commands as MCP tools (Connect an agent from outside; every tool: Every Wazza OS MCP tool).
    $ wazza --gui status
$ wazza --version

    Check this computer#

    wazza --check runs the same checks as the first start, without starting Wazza OS and without a screen: KVM, the systemd user session, the X11 display, the Chat sandbox, the graphics driver and the VM display buffers. Each line says what was found, what it means, and the commands that fix it.

    $ wazza --check
$ wazza --check --json

    Exit 0: nothing missing; 1: something is missing (VMs or the window would not start). A limited item (for example software graphics) does not fail the check. What each item means: First start › What is checked.

    Set up without clicks#

    A setup file does the first start's steps: your Wazza OS account, plan logins, API keys, apps, and appearance. Write it once and run it on every computer:

    {
  "account": {"email": "me@example.com", "passwordFile": "~/secrets/wazza-password"},
  "logins": ["claude", "chatgpt"],
  "keys": [{"provider": "openrouter", "name": "work", "keyFile": "~/secrets/openrouter.key"}],
  "whenOneRunsOut": {"openrouter": "take turns"},
  "apps": ["gimp", "blender"],
  "vm": {"memory": "auto", "cpus": "auto"},
  "appearance": {"theme": "dark", "glass": "reduced", "reduceMotion": false},
  "tabs": {"limit": 0}
}
    $ wazza --gui setup run --file ~/wazza-setup.json
$ wazza --gui setup status
$ wazza --gui setup reset-first-run
    FieldWhat it takes
    accountemail, and passwordFile (a file holding the password) or passwordStdin: true; never the password itself
    loginsPlan logins: claude, chatgpt, grok, google, openrouter, nous
    keysAPI keys: provider, an optional name, keyFile; never the key itself
    whenOneRunsOutPer provider: in order, take turns, least used, random
    appsApp ids to install (wazza --gui app list shows them)
    vmOnly "auto" (numbers are set in Settings or with the commands below)
    appearancetheme dark, light or system; glass on, reduced or off; reduceMotion
    tabs.limitTabs before they fold: 0 = Auto, up to 99

    It runs only the steps not done yet, so running it twice changes nothing. Each step prints one line as it ends: ✓ done, → waiting for you (a login prints its link and reads the code you paste in the terminal), ✗ failed. Exit 0: all done; 1: a step needs you or failed; 2: the file is malformed (nothing ran). --file - reads the file from standard input; --json prints one JSON line per step.

    VMs#

    $ wazza --gui vm list
$ wazza --gui vm create
$ wazza --gui vm start vm-2
$ wazza --gui vm stop vm-2
$ wazza --gui vm backup vm-2
$ wazza --gui vm backups
$ wazza --gui vm backup-inspect ~/Downloads/wazza-vm-2-2026-11-04-1200.zip
$ wazza --gui vm restore BACKUP_ID --start
$ wazza --gui vm restore ~/Downloads/wazza-vm-2-2026-11-04-1200.zip --into vm-1 --yes
    CommandDoes
    vm listEvery VM by number, running or stopped, with its disk
    vm createA new stopped VM with the lowest free number
    vm start VM, vm stop VMStart or stop one, vm-2 to vm-8 (vm-1 starts and stops with Wazza OS itself); a stop keeps its disk. A VM still starting is stopped at once: vm-2 was starting: its start is ended now (it never runs); its QEMU closes within seconds, and its row then says vm-2 was stopped while it started (its boot); it never ran. A stop that cannot happen says so, and that the VM still runs: vm-2 did not stop; it still runs, nothing was stopped
    vm backup VM, vm backupsA zip of the VM in your Downloads, its data disk too when it has one (in the background); the list of backups, each with its data disk's size when it holds one
    vm backup-inspect PATH.zipWhat a backup zip holds (its VM, when it was made, its disk, its data disk if any) and whether this computer's base image takes it; a read: nothing changes
    vm restore BACKUP_ID or PATH.zipA new VM from a backup (the id vm backups lists, or a backup's zip from anywhere on this computer), stopped, with the backup's data disk when it holds one; with --start, started once its disk is made. It answers at once; vm backups follows the job and vm list the VM
    vm restore … --into VM --yesReplaces a stopped VM's disk (vm-2 to vm-8) with the backup's, for good; with --start it then starts on it, its own disk put back if that start fails. A backup that holds a data disk replaces the VM's data disk too; one without leaves the VM's own as it is. Without --yes it is refused and says what it would replace (here a backup that holds a data disk): vm restore BACKUP --into vm-2 replaces vm-2's disk and everything in it with the backup's, for good; vm-2's data disk is replaced by the backup's too: … add --yes
    vm restore … --into vm-1 --yesReplaces vm-1: the backup is checked while vm-1 runs, then vm-1 stops (every running VM's apps and Chats end), takes the backup's disk and starts again; if it does not start on it, its own disk is put back. Without --yes it is refused (exit 2) and nothing is done
    vm reset VM --yesMakes a stopped VM (not vm-1) new at its next start: its disk is removed
    vm delete VM --yesRemoves a stopped VM (not vm-1) and its disk, for good

    Start from a backup#

    On a new computer, or after Remove all data, Wazza OS can make its vm-1 from a backup at its very first start, with the setup skipped (the first start's own Start from a backup… does the same by clicks). These start Wazza OS itself, so they take no --gui:

    $ wazza --vm1-backup ~/backups/wazza-vm-1-2026-11-04-1200.zip
$ wazza start --vm1-backup ~/backups/wazza-vm-1-2026-11-04-1200.zip
    CommandDoes
    wazza --vm1-backup PATH.zip or BACKUP_IDStarts Wazza OS with vm-1 made from the backup (a zip, or the id vm backups lists) before its first boot. Only while vm-1 has no disk yet: otherwise it is refused before any window opens (exit 1, the reason on standard error) and nothing changes. A backup that holds a data disk is refused the same way while vm-1 has a data disk of its own, which it would replace: vm-1 has a data disk, and the backup's data disk replaces it for good: replace it (replace: true; the CLI's --yes), or make a new VM from the backup (vm restore PATH). Nothing was changed
    wazza --vm1-backup PATH.zip --replace-vm1 --yesThe same when vm-1 already has a disk: vm-1's disk is replaced by the backup's before vm-1 starts, for good (its own disk is put back if it does not start on it); its data disk too when the backup holds one
    wazza start --vm1-backup PATH.zipThe same as wazza start (on a desktop its window, on a server its own virtual screen), with vm-1 from the backup; refused (exit 1, JSON) when Wazza OS already runs: use vm restore PATH.zip --into vm-1 --yes then

    A relative path is taken from your shell's folder. A zip that is not a Wazza OS VM backup, or one made on another base image, is refused with its reason, and nothing changes.

    Memory, disk and graphics#

    $ wazza --gui vm-resources
$ wazza --gui vm-memory status
$ wazza --gui vm-memory auto 50
$ wazza --gui vm-disk set 64
$ wazza --gui gpu status
    CommandDoes
    vm-resources [--vm VM]What the VM has now and the most it may get, its graphics and disk, and your computer's processors, load, memory, graphics cards and free disk
    vm-memory status [--vm VM]The memory rule and each VM's memory and limit
    vm-memory auto PERCENT [--min MIB]Auto: PERCENT (10 to 100) of the memory free now, for every VM
    vm-memory set MIB [--vm VM]A fixed amount, in MiB, added to the running VM at once
    vm-disk status, vm-disk set GIB [--vm VM]The disk's size; grow it (only grows: a running VM grows at once)
    vm-gpu status, vm-gpu auto PERCENT, vm-gpu set MIBThe graphics memory a VM may hold
    gpu status, gpu mode virtualized|native|none, gpu card …The GPU setting (Desktop apps and the GPU)

    The same settings, explained: Settings › VM resources.

    Keys and sign-ins#

    $ wazza --gui wazza-account login --email me@example.com --password-stdin < ~/secrets/wazza-password
$ wazza --gui provider-keys add --stdin < ~/secrets/keys.json
$ wazza --gui provider-keys list --credit
$ wazza --gui provider-signin status

    keys.json holds {"keys": [{"providerId": "openrouter", "key": "…"}]}; keep it readable only by you, or pipe it from your password manager. Also: provider-keys remove PROVIDER, wazza-account status and logout, copilot key-from-gh (GitHub Copilot from your gh sign-in). Plan logins that open a browser are easiest with the setup file above. Details: Sign in › From the command line.

    Chats#

    $ wazza --gui chat-model set openrouter/xiaomi/mimo-v2.6-flash
$ wazza --gui chat-transcript --tab t5 --last 4
$ wazza --gui chat-transcript --tab t5 --kinds tool,bash > t5-tools.json
$ wazza --gui timeouts set --command 1800
    CommandDoes
    chat-model status, chat-model set MODELThe model new Chats start on (a Chat keeps its own)
    chat-transcript --tab TAB [--vm VM]A tab's whole conversation as one JSON document, oldest first: --kinds user,message,thinking,tool,bash,error, --roles user,assistant, --contains TEXT, --from N, --last N
    chat-queue list|edit|discard … --tab TABThe messages waiting while a Chat answers
    schedule list, schedule cancel IDMessages the Chats scheduled for later
    timeouts, timeouts set [--tool S] [--command S]The time limits: a tool call 10 to 1800 s (default 60), a command 10 to 7200 s (default 600)
    local-services status|on|offWhether Chats on your computer may reach its local services

    Tab ids (t5) come from the window's tabs_read action (below). To send a message to a Chat: the window action chat_send.

    Apps#

    $ wazza --gui app list
$ wazza --gui invoke modules_call packages install_request '{"appId":"gimp","vmId":"vm-1"}'
$ wazza --gui app status gimp --vm vm-1 --refresh
$ wazza --gui app uninstall gimp --vm vm-1 --focus
    CommandDoes
    app list, app get APP_IDEvery app, and one app's recipe
    install_request (above)Installs an app, in the background (a failed install is tried once more)
    app status APP_ID [--vm VM] [--refresh]Installed or not; --refresh checks the VM itself
    app uninstall APP_ID [--vm VM] [--focus] [--follow]Shows the uninstall's confirmation in Wazza OS (only your click there uninstalls); --follow waits for the result
    app observe JOB_ID --followAn install's or uninstall's live output
    app template, validate, save, removeYour own apps (Add your own apps)

    Files#

    $ wazza --gui explorer list Documents --vm vm-1
$ wazza --gui explorer copy-to-vm ~/report.pdf --vm vm-1 --folder Documents
$ wazza --gui explorer upload Pictures/circle.png --vm vm-1
$ wazza --gui clipboard files --to-computer allow
    CommandDoes
    explorer list [PATH] [--vm VM]A folder of the VM's home (works for a VM in the background)
    explorer rename, move, delete PATH --yes, permissionsAs in the Explorer; never overwrites; delete is permanent
    explorer copy-to-vm PATH… [--vm VM] [--folder F]Your files into the VM (default ~/Downloads), by your copy rule
    explorer upload VM_PATH… [--vm VM]The VM's files to your computer, as new files (default Downloads/From the VM), by your copy rule
    explorer list|details|open|search|read … --computerYour own files, below your home
    clipboard copy --stdin [--guest-only]Puts text on the VM's clipboard (and yours)
    clipboard files [--to-vm R] [--to-computer R]The file-copy rules: ask, allow, off; and --background-chats on|off: may the Chats of a VM you are not viewing copy files (Files & sharing)

    The window, and everything else#

    Every action of the window has a name, and ui do runs it with its arguments; ui catalog lists them all (about 200: open an app, read the tabs, send to a Chat, read what you see, start a VM, read the settings…).

    $ wazza --gui invoke modules_call ui catalog '{}'
$ wazza --gui invoke modules_call ui do '{"action":"tabs_read","args":{}}'
$ wazza --gui invoke modules_call ui do '{"action":"open_app","args":{"appId":"inkscape"}}'
$ wazza --gui invoke modules_call drive look '{"vmId":"vm-1","tabId":"t3"}' --image-out ./t3

    Arguments larger than a command line holds: - reads them from standard input, @file.json from a file. Also: data status (Wazza OS's folders on your computer and their sizes), data remove-all --confirm "REMOVE ALL DATA" (Remove all data), quit. On a server, screenshot and record capture Wazza OS's own screen (Wazza OS on a server).

    When an agent runs these commands#

    A command run by the agent of a Chat (from its shell) is that Chat's: it may not change your view (focus, quit), reach another tab's Chat, copy files for another VM, or do what only you can do (Let this Chat edit my files, loosening the file-copy rules, Local services on). An agent outside Wazza OS that you started yourself runs the commands as you, in its shell or through wazza-os mcp (Connect an agent from outside).
